# Decisions (one line each)

## Source-document discrepancies (found during inspection, 2026-10-31)
- D-01 `docs/ForgeTrace_Dossier.pdf` does not exist; the dossier is `ForgeTrace — Research & Implementation Dossier-2.pdf` at repo root and is used as the authority.
- D-02 The dossier has 22 sections; the requested sections 23 (dataset schema), 24 (ground-truth format) and 25 (CLAUDE.md) do not exist. Schema follows §13, ground truth follows the format in the task prompt, CLAUDE.md is derived from §18's working rules.
- D-03 `docs/PRD_Kill_Chain_Attack_Path.pdf` does not exist; PRD requirements are taken from the dossier's PRD-derived §2 and the task prompt.
- D-04 `tools/edr_log_generator.py` does not exist; `tools/gen_scenarios.py` reimplements a benign SimEDR-style generator whose output shape mirrors `edr_events.json` (ECS-like JSON). No reference generator was created or modified.
- D-05 `firex-30G.log.manifest.json` describes `firex-30G.log` + `firex-30G.win.jsonl`; neither is present, so the manifest cannot score the local `firex-10G.log`. Used only to understand the ground-truth shape (1-based lines, 0-based byte offsets, per-event `[line, byte, stream]`).
- D-06 `firex-10G.log` is FortiGate key=value text (not JSON/CEF) up to roughly byte 4.8 GB; sampled lines beyond that are binary (truncated or corrupt copy). Full-tier ingestion is deferred to Phase 2.
- D-07 `edr_events.json` vendor alerts carry `threat.*`, `rule.*`, `labels*`, `event.kind=alert`, `event.severity`; field_map.yaml never maps these, so they cannot reach the envelope or the rules.

## Engineering
- D-10 Stack: Python 3.11 venv, pinned in requirements.txt; httpx not installed (not approved) so API tests drive a live uvicorn via urllib.
- D-11 `line_digest` = SHA-256 hex of the raw line bytes without the trailing newline (dossier §13 suggests xxhash64, which is not in the approved stack; §3 names SHA-256).
- D-12 `event_id = (file_id << 48) | byte_offset`, file_id assigned 1..n by sorted input path; ground truth is generated with file_id=1 because the sample is a single file; scorer matches on line_no and also checks event_ids.
- D-13 Envelope additions beyond §13 forced by the scenarios: `host_ip`, `src_is_external`, `registry_path`, `registry_value`, `group_name`, `parent_process`, `byte_offset`, `line_no`, `raw_format`, `source_event_id`.
- D-14 Canonical user = lower-case bare account (domain stripped into `user_domain`) so `user` and `target_user` compare directly; dossier §11 suggests `domain\user`, but the dev data is single-domain.
- D-15 Ingest is single-process streaming (readline, 200k-row Parquet batches, zstd, 128k row groups); byte-range workers deferred to Phase 2.
- D-16 FortiGate key=value parser included in field_map/parsers so firex lines normalise, but full-tier runs are Phase 2.
- D-17 `ts` is stored as naive TIMESTAMP(us) holding UTC (tz-aware results would require pytz, which is outside the approved stack).
- D-18 Rule types: match, threshold (+followed_by), and a minimal `baseline` (first_seen after warm-up, dossier §12 table) needed for R008; `sequence` deferred.
- D-19 Added R010 (T1204.002, Office app followed by a script interpreter it spawned) beyond the brief's list so the A2 "winword.exe" step is detectable; R010 number was unused.
- D-20 Thresholds: R001 ≥20 fails/10 min per src_ip; R001c ≥5 fails/30 min per (src_ip,user) followed by success ≤30 min; R009 ≥10 conns/2 h per (host,dst_ip), bytes_out ≤2048, dst_ip contacted by ≤1 host; R011 bytes_out ≥100 MiB external; R008 warm-up 6 h.
- D-21 label_priority (lower wins): R002 15, R001 20, R001c 25, R003/R005/R009/R011 30, R010 35, R006/R007 40, R008 50, R004 90.
- D-22 Duplicate suppression (§12 step 1) at detection level: a detection whose members are a subset of a stronger same-technique detection gets duplicate_of and is excluded from correlation (R001 ⊂ R001c on A1).
- D-23 followed_by semantics: follower must occur within `within` after ≥count window members; members = those members + follower.
- D-24 Technique table is a hand-curated ATT&CK subset in config/attack.yml (STIX build script deferred); rule load rejects unknown techniques and invalid technique/tactic pairs.
- D-25 Correlation weights, reason weights, τ, P matrix, F saturation (500), θ_edge 0.45, K 3 are the dossier §12 defaults (config/correlation.yml); τ = 2 h only when same_user is the sole reason (matches the §12 worked example, which uses 30 min with same_user+same_host).
- D-26 Max candidate window 6 h (brief) instead of per-reason windows; skew tolerance 60 s.
- D-27 entity degree (F term): user→distinct hosts, host→distinct users, ip→distinct hosts using it as src/dst, domain→distinct hosts; strongest linking entity = highest reason weight, ties → highest degree (conservative).
- D-28 Detections whose member events all carry a different primary technique (label priority) are folded into the primary group as `also_matched` rather than becoming separate nodes (e.g. R004 on the R003 event, R008 on the R002 event).
- D-29 raw_alert_count = number of detections merged into the group (aggregation gap 15 min); member_event_count reported separately.
- D-30 Primary path = all incident groups ordered by (ts_first, tactic ordinal, first event_id) as the brief's Step 5 specifies; each hop cites its kept edge or says none exists. The dossier §12 step 8 DP (J = Σ log s + λ Σ n, λ = 1) is kept as `strongest_chain`; with dossier defaults it drops weakly-linked tail steps, so it is reported but not used as primary. Conflict noted deliberately.
- D-31 Abstention gate = ≥ 2 distinct tactics (brief); the dossier's alternative "critical group + corroboration" route and θ_incident/θ_path are not used in Phase 1.
- D-32 Risk (WP-17): 100 × (0.35·maxsev/4 + 0.25·max node criticality + 0.20·deepest ordinal/14 + 0.20·critical reachable/total critical); bands high ≥ 70, medium ≥ 40.
- D-33 Reachability per §14: compromised set from incident groups (actor accounts and hosts 1.0; accounts created/modified by them 0.5); edges ADMIN_TO observed (interactive/RDP logon, or add to local Administrators) 1.0, fixture ADMIN_TO/MEMBER_OF/GROUP_ADMIN_TO 0.7, CREDENTIAL_EXPOSURE (interactive session on host, 7-day lookback) 0.5; hop limit H = 4 graph edges (dossier) rather than the brief's "1–2 hops"; report reach ≥ 0.3, critical = criticality ≥ 0.8; network factor not modelled (treated as 1.0).
- D-34 Only disable_account is simulated in Phase 1 (isolate_host, block_ip, revoke_session rejected with an explicit error). Candidate ranking evaluates disable_account for every account in or on a path from the compromised set (≤ 20).
- D-35 total_critical_assets = hosts named in the fixture with criticality ≥ 0.8.
- D-36 API: brief's `/incidents/{id}/reach` plus dossier alias `/reachability`; `/alerts?unlinked=true` and `/rules` included; `/report` and `/metrics` deferred. Strict CSP (script/style 'self'); all log-derived strings rendered with textContent; Cytoscape canvas labels are not HTML.
- D-37 event_id values stay below 2^53 for file_id < 32, so they are exact as JavaScript numbers in the dashboard.
- D-38 Scoring: step found = any detection (incl. duplicates/folded) whose members intersect the step's lines; predicted label = the step events' primary technique; path order evaluated on the primary path with the dossier DP chain reported as a secondary line; runtime/peak RSS read from run_stats.json (ru_maxrss of the single run process).
- D-39 FortiGate timestamp = `date`+`time`+`tz` (explicit offset); `eventtime` in firex encodes local wall-clock as if UTC (e.g. 08:48:26 for tz +0530), verified on the first line.
- D-40 followed_by gained an optional `link` (follower field == window field), used by R010 for the process-tree link (follower parent_process == Office process); found when running on edr_events.json, where unlinked Office launches inflated R010 members.
- D-41 Edge evidence IDs are computed only for kept edges (correlation on edr_events.json went from 7.1 s to 0.2 s).
- D-42 Workspaces: each analysis writes to `out/<workspace>/` (`sample` = data/sample/events.log, `input` = the data/input/ drop folder); the API serves any workspace via `?ws=`; FORGETRACE_OUT pointing at a single result dir still works (single-workspace mode).
- D-43 Uploads use a raw request body (`POST /inputs?filename=`) streamed to disk, because multipart parsing would need python-multipart (not in the approved stack). Names must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` with a log suffix; writes go to a temp file then an atomic rename; no overwrite unless `overwrite=true`; 8 GiB cap.
- D-44 Background analyses run in a server thread, one at a time; reads of the workspace being rebuilt return 409. Peak RSS for API-started runs is the server process's ru_maxrss (includes the server), so `make run` remains the reference measurement.
- D-45 UI colour follows the dataviz reference palette: one blue for single-series bars, status colours only for state and always paired with a text label; dark mode uses its own token set.
- D-46 Demo walkthrough: `data/demo/demo_events.log` (5 hand-written events: 3 ECS JSON + 2 CEF, one benign) is committed and analysed into workspace `demo` (`make demo` or the dashboard). `GET /walkthrough?ws=demo` returns each stage's stored output plus a re-parse of each raw line used only to show the vendor-field → envelope-field trace; it refuses workspaces over 200 lines. Candidate edges now persist src/dst, weighted terms, Δt, τ, strongest entity and prune reason so dropped pairs can be explained. Pinned by tests/test_demo.py.

## Phase 2 (docs/PHASE2.md)
- D-47 EV-0: frozen interfaces are Pydantic v2 models with Arrow schemas in `forgetrace/models.py` (Event, Reason, Detection, AlertGroup, RunPlan, DisabledDetector). GroundTruth (Attack, Step, LineRef, AuthEdge) lives in `forgetrace/eval/groundtruth.py`, so nothing on the detection path can import it. `test_ground_truth_not_imported_by_engine` now allows only `forgetrace/eval/` and `forgetrace/datasets/` to reference ground truth, and also bans `forgetrace.eval` imports elsewhere.
- D-48 Rule detections carry `detector = "rule:<id>"`, `score = rule confidence` (the rule's prior; fusion replaces it in FU-2) and one reason holding the matched-condition text. Alert groups carry `p_malicious = null` and `contributions = {}` until FU-2.
- D-49 The envelope gains a `dataset` column (`forgetrace run --dataset`). Workspaces built before this change lack it; re-run them.
- D-50 A GroundTruth step needs at least one locator: `event_ids` (generated data), `line_refs` (AIT line labels) or `edges` (LANL red-team user/src→dst/time). Phase 1 GT files convert via `ground_truth_from_legacy`.
- D-51 Benchmarks: `tools/bench.py` reports peak RSS both as psutil 1 s sampling over the process tree (PHASE2 definition) and as ru_maxrss; py-spy needs root on macOS, so the STEP 0 profile used cProfile (`data/bench/prof150.out`, 150 MB slice).
- D-52 EV-1 metric definitions. A step is found if any detection (duplicates and folded ones included, as D-38) has a member among the step's events; otherwise the same-host ±60 s fallback applies and is reported separately (`found_by`, `step_recall_event_only`). Predicted label = majority primary label over the step's events (ties → lexical order). Ordered = no found step missing from the chosen incident path and no discordant pair (ties allowed, as in Phase 1). Kendall τ is tau-a over placed found steps. Purity and ARI are computed over non-duplicate detections: truth = majority attack, else a unique benign class; predicted = incident, else a singleton. Nodes = alert groups. NDCG@10 uses binary relevance. ML score unit = detection, positive if any member event is malicious; Recall@B uses the top B per calendar day of `ts_first`. The PRD label target is judged on the exact sub-technique; the parent level is reported beside it.
- D-53 Bootstrap: percentile, 1,000 resamples, seed 0. Attacks pooled across seeds for recall, label accuracy and ordered paths; incidents pooled for the false-alert rate. p95 path latency is measured on the `/incidents/{id}/path` handler in-process (no HTTP stack), 20 calls per incident. `time_to_first_incident` equals the wall time until SC-4 adds micro-batches.
- D-54 `make check` = ruff (E, F, W; 140 columns; per-file ignores only for Phase 1 files kept as written) + pytest. `make run DATA=` is accepted (`INPUT=` still works); `make eval DS= EXP= [GT= RUN=]`; `make bench DATA= BENCH=`.
- D-55 EV-2: the D0 suite is `tools/gen_suite.py` (subclass of the Phase 1 generator; the seed-7 dev sample is unchanged). Split by seed: 1–10 tuning, 11–20 test, never mixed. Generated logs are gitignored; `data/d0/suite.json` records each seed's sha256 so regeneration is checkable. Ground-truth step order is the time order of each step's first event.
- D-56 A3 deliberately uses techniques no Phase 1 rule covers (T1069.002, T1560.001, T1567.002), and decoys D2 (typo burst + success, which crosses R001c) and D3 (admin RDP + encoded PowerShell, which crosses R003/R008) are deliberately hard. E0 is expected to lose recall and precision on them; that is the measurement, not a bug.
- D-57 STEP 0 baseline (Phase 1 code, 1 worker, first generated 10 GB file): ingest ≈ 15.5 min; detection did not finish in 54 min and the run was stopped by the owner at 1 h 09 min. Root causes: (a) the threshold-window merge rescanned all earlier events of a key per qualifying event (O(k²); R010 has count 1, so every Office launch opens a window); (b) followed_by scanned each window per follower and every follower per window; (c) duplicate marking compared all detection pairs; (d) candidate edges paired every two groups sharing an entity before applying the 6 h window; (e) edge evidence ran one query over all Parquet parts per edge × reason × endpoint; (f) timeline and primary-path lookups were per-event/per-hop list scans; (g) reachability built its context graph twice per incident from full scans; (h) persistence inserted one row per statement.
- D-58 All of (a)–(h) replaced by linear or indexed equivalents with identical output: hypothesis tests against verbatim copies of the Phase 1 algorithms (tests/test_engine_windows.py) and byte-identical detections, groups, edges, labels and incidents on the dev sample, five D0 seeds and edr_events.json. Reachability now reads a `reach_events` table (successful logons + group adds) materialised once per run; old workspaces fall back to `events`. When a prebuilt graph is passed, `reachability()` derives the fixture flag from config instead of assuming one (fixes the observed-only label in the simulate path).
- D-59 Ingest is parallel: line-aligned 64 MB byte ranges, a parallel newline count assigns each range its first line number, a spawn-based process pool parses ranges (default workers = CPU count − 1; 9 on the M2 Pro's 6P + 4E cores, `FORGETRACE_WORKERS` overrides), each range writes its own Parquet file and parse-error file, whole-file SHA-256 runs in a parent thread. Inputs under 128 MB stay in-process. Rows are identical to a sequential pass for any range size or worker count (tests/test_parallel_ingest.py). Per-line normalisers (IP, user, host, internal-network test) are memoised (bounded LRU) and event-type rules precompiled: 21.5 → 29 MB/s per worker.
- D-60 The first bulk generator was unrealistic (19 users and 10 external IPs for 15.4M events; ~240 failed logons per user-day → 34k brute-force windows). `tools/gen_bulk.py` now scales the population with volume and draws failures per user-day, and builds days in parallel. The owner then supplied real datasets (`data/input/firex_logs/firex-10G.log`, `data/input/firex-50G.log`), which replace generated files for scale runs.
- D-61 Correction to D-06: the supplied `firex-10G.log` (6,543,120,032 bytes) and `firex-50G.log` (32,702,905,053 bytes) are clean FortiGate key=value text to the last byte (sampled every 1/40 of each file; no NUL bytes; both end on a complete line). Data artifact found instead: from roughly 35% of each file onward every line carries the same `eventtime=1793350105999999000` (2026-10-30 08:48:25.999999 +05:30) — apparently the generator's end-of-window clamp. Time-window rules see that region as one instant; measured share reported with the scale runs.
- D-62 Graph store (owners' decision, on the mentor's recommendation): **hybrid**. Raw events stay in Parquet/DuckDB (columnar time-window scans, byte-offset evidence). **Neo4j Community 2025.09** holds the relationship layer: users, hosts, IPs, domains, groups, alerts (alert groups), techniques/tactics, incidents; relationships LOGGED_ON, FAILED_LOGON, ASSIGNED_TO, CONNECTED_TO, INVOLVES, MAPS_TO/IN_TACTIC, LEADS_TO (kept correlation edges with score terms and evidence), CONTAINS, PATH_STEP, ADMIN_TO, MEMBER_OF. Every relationship carries raw event_ids (≤ 5 samples on aggregated relationships; full evidence ids on LEADS_TO). Server via `deploy/neo4j/docker-compose.yml` (localhost-only ports, dev password overridable by `NEO4J_PASSWORD`); Python driver `neo4j==6.4.1` (owner-approved dependency). Detection and correlation still decide in DuckDB/Python; the graph is loaded after correlation and never decides.
- D-63 Graph scope is configured in `config/graph.yml`. Measured on firex-10G: 9.9M distinct src→dst IP pairs and 8.3M distinct destination IPs, so loading every connection would put ~18M nodes and ~10M relationships per 10 GB in the graph. Default scope: all internal↔internal connections (lateral-movement candidates; 90 pairs on firex-10G) plus every connection touching an alert IP; `connections.all: true` loads everything. Adding `config/graph.yml` changes the config hash of every run from this commit on.
- D-64 Graph keys are `uid = "<workspace>|<kind>:<natural key>"` under uniqueness constraints (Community edition supports property uniqueness, not node keys), written with batched `UNWIND $rows MERGE` (10k rows per transaction, parameters only). `replace=True` (a full re-run) clears the workspace subgraph first; `replace=False` merges, which is the hook for live micro-batches. Reload is idempotent (tests/test_graph.py). `forgetrace run --graph` / `FORGETRACE_GRAPH=1` loads after correlation; an unreachable server skips the step with a reason and never fails the run. API: `/graph/status`, `/graph/incidents/{id}`, `/graph/neighbors?key=user:<name>`, `/graph/reach?user=`.
- D-65 Long-running commands report progress: `forgetrace run` prints stage, percent, elapsed and ETA on stderr (at most every 5 s per stage) unless `--quiet`; the graph loader reports rows written per step.
- D-66 firex ground truth: `firex-30G.log.manifest.json` is seed 2 and does not match firex-10G/50G (none of its external attacker addresses occur in firex-10G), so accuracy on 10G/50G is N/A; the owners are obtaining `firex-30G.log` + `firex-30G.win.jsonl`. `forgetrace/datasets/firex/adapter.py` turns a manifest into GroundTruth: one attack per incident, one step (the manifest does not split chain events by stage), every `at` event as a (file, line) reference by stream; incidents without `at` (floods) are scored on their first and last line and marked range_only; local times converted to naive UTC. A label counts as correct if it matches any technique listed in the step ("A, B" alternatives or "A -> B -> C" chains).
- D-67 Envelope gains behavioural firewall fields (frozen Event interface extended, per the change rule): copied `message` (msg/logdesc), `service`, `log_subtype`, `src_country`, `dst_country`; derived `src_subnet24`, `src_subnet16`, `domain_base` (last two labels), `dns_label_max` (longest label), `local_hour` (ts shifted by `local_utc_offset_minutes`, 330 for the firex site). FortiGate verdict fields (attack, attackid, virus, catdesc, apprisk, crscore, severity, level) stay unmapped, so rules cannot read them (owner decision: behaviour only).
- D-68 Threshold rules take one of three metrics over the sliding window: `count` (default), `distinct: <field>` (count of distinct values ≥ count) or `sum: <field>` (total ≥ min). Window merging and followed_by are unchanged.
- D-69 FortiGate behaviour pack `config/rules/firewall.yml` (F001–F017), written from the 30G manifest's scenario descriptions and the shapes seen in firex-10G (development set, seed ≠ 2), to be scored once on firex-30G (held-out, the only labelled firex set). Every F-rule requires `source_type = firewall` (first step of the FU-1 router; they never fire on endpoint data — tested). Not covered, reported as blind spots: malware download (needs the AV verdict), insider drift (needs a per-account baseline of server reach, ML-1/ML-2), web shell in use (needs request method/body), HTTP flood (no rate signal distinguishable from the 69% timestamp clamp), and the six Windows-stream scenarios until the Windows log is ingested. 20 ATT&CK techniques added to config/attack.yml. Two FortiGate event types added: VPN tunnel-up → `vpn_login`, IPS-inspected request → `http_req`.
- D-70 Long-range correlation (mentor's reason for the graph): `forgetrace/graph/campaigns.py` adds RELATED edges between alerts sharing a User/IP/Domain that occurs in 2–25 alerts, at any time gap, and turns connected components of LEADS_TO ∪ RELATED spanning ≥ 2 tactics into :Campaign nodes (docs/wp/GR-2.md). Incidents are unchanged. On firex-10G: 4 campaigns, 3 spanning more than 6 h; one joins XSS, SQLi, command injection, traversal, port scan, lateral sweeps and staged exfiltration over 129 h; one is a coincidental link through the VPN gateway address (reported, not hidden).
- D-71 Streaming mode `forgetrace stream` (docs/wp/SC-4.md): line-aligned byte batches, parallel ingest per batch with continuing line numbers, full re-analysis over accumulated data per batch, optional `--follow` for growing files, `stream_status.json` / `GET /stream/status` with time to first incident. Equivalent to a batch run (tests/test_stream.py).
- D-72 Threshold rules filter groups in SQL (`QUALIFY max(win_count) OVER (PARTITION BY keys) >= threshold`) so groups that never reach the threshold never leave DuckDB; output unchanged (rule fixtures, equivalence tests, byte-identical detections on the dev sample, D0 seeds and edr_events.json; only the config hash inside incidents changed because config files were added).
- D-73 Graph connection scope default changed from "either end is an alert entity" to "both ends are alert entities" (attacker ↔ victim): with the FortiGate pack the former loaded 928,915 IP nodes for firex-10G (graph load 116 s), because flagged internal hosts and the public web server talk to hundreds of thousands of addresses.
- D-74 Timestamp clamp effect (D-61) on rules, measured on firex-10G: R001 (321 groups, 1.2M member events) and F002 (one group, 915k members) are dominated by the 69% of events pinned to one instant, which places every source's failed logins inside one window; the two incidents emitted on firex-10G are made of these groups. Not corrected in Phase 2 code; to be judged against firex-30G labels.
- D-75 Incident records are bounded: each node embeds at most 10,000 member ids (200 when the incident has more than 50 nodes) (`member_event_ids_truncated: true` beyond that) and the timeline at most the first and last 100 member events of each group when an incident has more than 2,000 member events (`observed.events_truncated` says so); full membership stays in `alert_groups` and `GET /incidents/{id}/events` pages it. Compromised-set evidence takes the 50 smallest ids from each sorted group head instead of building a set of the whole group. `forgetrace eval` reads full membership from `alert_groups`, so metrics are unaffected. On firex-50G the unbounded version stalled for over 10 min in incident building (timestamp-clamp groups with millions of members); outputs below the bounds are byte-identical (dev sample, edr_events.json).
- D-76 The bounds are per incident, not only per group: on firex-50G the timestamp clamp chained ~4,500 brute-force groups into one incident whose record was 463 MB (timeline 293 MB, edges 136 MB, nodes 71 MB) and DuckDB ran out of memory parsing it. Now the timeline holds at most 2,000 events per incident (an equal head/tail share per group), node member lists 200 ids when an incident has more than 50 nodes, and edges keep 10 evidence ids each when an incident has more than 500 edges (`evidence_event_ids_truncated` gives the full count; the edges table keeps all ids).
- D-77 Edge storage is bounded. An edge is scored on all its shared entities, but stores the 20 strongest reasons (by weight, then entity key) plus `reasons_total` and per-type `reason_counts` when it has more; on firex-50G edges had up to 957 reasons (avg 50) and the candidate-edge table held 3.3 GB of reasons JSON, which exhausted DuckDB's 4 GB during persistence. When there are more than 100,000 candidate edges, the table keeps every kept edge plus the 100,000 highest-scoring dropped ones (run_stats still counts all). Outputs on the dev sample and edr_events.json unchanged (no edge there has more than 20 reasons).
- D-78 `forgetrace analyse --out DIR [--graph]` re-runs detection → graph on an already-ingested workspace (rule tuning, fixes after ingest); run_stats records the reused ingest. `tools/bench.py --analyse-only` measures it.
- D-79 Unseen-format parsing. Lines are classified by syntax (JSON, CEF also behind a syslog header, syslog, key=value, CSV recognised by a header row). A named profile in field_map.yaml is used only when its `match` (syntax + required keys) fits; every other line is mapped through `config/field_aliases.yaml` (normalised field-name aliases, ordered timestamp candidates incl. split date/time/tz, outcome vocabulary, source-type heuristics, free-text message patterns for sshd/sudo/useradd/iptables-style text). Vendor verdict names (threat, attack, virus, severity, …) are on a never-map list. Generic lines get vendor-neutral event types from `~regex` conditions that apply only to `generic_*` formats, so existing profiles classify exactly as before (verified: 297,922 firex lines and all dev/EDR events parse identically, detections identical).
- D-80 Site facts live in `config/site.yaml` and are referenced by rules as `@site.<key>`: home countries (default `auto`: learned from where ≥ 80% of successful logins come from, needs ≥ 50 logins, plus the label used for private addresses), night hours, default UTC offset (0), default year for year-less syslog. F004 no longer contains country names. `local_hour` now uses each line's own UTC offset when it states one, else the site offset; previously the firex offset (+05:30) was applied to every line, which shifted local_hour for UTC-stamped EDR data (detections unaffected).
- D-81 Detector router (`forgetrace/rules/router.py`, FU-1): before detection it measures the capability profile (fill rate of each envelope field, event and source types present) and site values, enables only rules whose required fields, event types and site values exist, and writes `run_plan.json` (RunPlan: enabled, disabled with reasons, blind spots, learned site values) for human review. Required fields exclude aggregate_by.
- D-82 Live mode (`forgetrace live`, docs/wp/LIVE.md): watched files/folders are consumed in line-aligned micro-batches; per-batch work is the batch + `lookback_minutes` (60) of raw data. Config in `config/live.yml`.
- D-83 Rule state for live mode: threshold rules whose window (+ follower window) exceeds the lookback are evaluated on 5-minute bucketed partial aggregates (count, sum, distinct values capped at 5,000 per key and bucket); first-seen rules use a persistent key set with warm-up from the first event seen. Short rules run on batch + lookback; detections without a new event are discarded before merging.
- D-84 Knowledge base: alert groups merge into `kb_alerts` by (rule, aggregate key, overlapping time within the aggregation gap) with stable ids; `kb_edges` holds correlation edges between knowledge-base alerts of the last 6 h (dossier §12 score unchanged). The graph accumulates entity first/last seen and counts and relationship counts per batch; :Batch markers make a replay idempotent; incidents (LEADS_TO components ≥ 2 tactics) and campaigns (LEADS_TO ∪ RELATED) are recomputed after every batch with ids stable while they grow.
- D-85 Retention: raw Parquet older than `hot_days` (by event time vs the watermark) moves to `cold/` and stays usable as evidence by event_id; `cold_days` optionally deletes it. The knowledge base and graph are never pruned, so long-term dependencies outlive the raw data.
- D-86 Explanations (`forgetrace/report/explain.py`, mentor: manual verification without ground truth): every alert, incident and campaign gets a deterministic explanation built only from stored facts — headline and summary (who/where/when), the rule condition and threshold translated to English next to the observed numbers, raw evidence lines re-read by byte offset with file, line number and SHA-256 check, verification steps (sed/grep commands for the cited lines and entities, what to confirm), benign look-alikes and checks per technique from `config/explain.yml`, data-quality caveats (e.g. a timestamp shared by ≥ 1% of events), and for chains why each step links to the previous one (shared entities, gap, score). API: `/explain/alert|incident|campaign/{id}`.
- D-87 LLM narrative (`forgetrace/report/llm.py` + `tools/llm/openrouter.py`, standard-library HTTP, no new dependency): optional (`?llm=true`), restates the explanation only. Key from `OPENROUTER_API_KEY` only; entities replaced by HMAC tokens (key in `FORGETRACE_PSEUDO_KEY` or an untracked `data/.pseudo_key`) and raw log lines never sent; temperature 0, JSON schema; rejected unless every cited event id and technique, every token and every multi-digit number is in the payload and no raw address/e-mail appears; cached by (facts hash, prompt version, model); spend ledger with caps $1.50 lifetime / $0.25 per run; model `google/gemini-2.5-flash-lite` set in `config/llm.yml`. Without a key the deterministic explanation is returned with the reason. A test asserts no module outside forgetrace/report uses an HTTP client.
